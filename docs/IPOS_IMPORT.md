# iPos Import

## Product & iPos Import Schema v1

The deployed database schema is defined by [`supabase/migrations/20260928_product_ipos_schema_v1.sql`](../supabase/migrations/20260928_product_ipos_schema_v1.sql), migration version `20260928`. This document specifies the import contract.

### Application Phase 1 — upload and request

The `/import-ipos` workspace page is available to OWNER, ADMIN, and GUDANG. It accepts `.xlsx` files up to 25 MiB, uploads the original workbook into the private `quena-ipos-imports` bucket, and calls the authenticated `request_ipos_import(p_outlet_id uuid, p_storage_path text, p_original_filename text)` RPC. The RPC checks the caller's active role, validates that the object exists in the bucket and that its path belongs to the caller, then creates an `ipos_import_requests` row and returns its UUID. The page reads that request under the existing requester/manager SELECT policy to show its state and creation time. The follow-up worker migration retains a two-argument compatibility overload for older callers; such legacy requests use the generated object basename as their filename.

The object path is exactly `incoming/<authenticated-user-uuid>/<random-uuid>.xlsx`. Phase 1 uses the browser Supabase client with the normal authenticated user session and public anon key; it has no service-role credential. The outlet argument is resolved through the authenticated `outlets` read policy using the seeded `QUENA-MART-1` outlet. If upload succeeds but request creation fails, the UI reports the partial result and offers a retry against that same object; the pending path is retained in tab session storage when available and the file cannot be replaced until the request is created. It does not try to delete the stored workbook because authenticated deletion is intentionally denied.

Phase 1 only uploads the original file and creates/displays a request. It does not parse workbook cells, create import batches or rows, change product/pricing/HPP/inventory data, or create audit findings. A queued request does not mean that products have been imported.

### Application Phase 2A — trusted raw snapshot worker

Phase 2A code consists of a server-only worker core (`src/lib/ipos/worker.ts`) and a manually invoked Node route (`POST /api/internal/ipos-import`). The route requires a bearer value from `IPOS_IMPORT_WORKER_SECRET` (at least 32 characters); the worker also requires the server-only `SUPABASE_SERVICE_ROLE_KEY` and the project URL. These values must be configured only in the server runtime. The route accepts one request UUID; it is not called by the browser UI, and production execution is manually controlled.

The worker uses `20260928115000_ipos_worker_v1.sql`; Phase 2A is verified complete for the real request and batch recorded in the project run notes. Its `claim_ipos_import_request(uuid)` function conditionally claims only QUEUED requests and creates exactly one PROCESSING batch in the same PostgreSQL transaction. Concurrent calls cannot both claim a request. A later invocation reports an existing PROCESSING/terminal state without duplicating the batch or rows. The worker downloads the object's bytes through trusted private Storage access, validates the 25 MiB boundary, XLSX/ZIP signature, the `Satu Harga` sheet, exact row 1 control markers, all 24 unique known headers on row 2, and rejects populated data outside those header columns. It calculates the SHA-256 and writes raw rows in chunks of 100. The `complete_ipos_import_request` function checks count, contiguous source row numbering, RAW_ONLY status, and null product links before atomically marking batch and request COMPLETED. Caught failures record a bounded error and row count, and atomically mark both records FAILED. Any partial rows remain immutable evidence on a FAILED batch.

`raw_data` has exactly the 24 source-header keys. Strings are kept as strings (including whitespace and malformed/control-character content), numeric Excel cells as finite JSON numbers, booleans as booleans, and missing/blank cells as JSON null. No SKU trimming, numeric parsing, barcode cleanup, or product interpretation occurs. Header order may change because the parser maps values by header name; missing, duplicate, or unknown nonempty headers fail validation. Empty internal worksheet rows before the last populated row are stored with 24 nulls to preserve source Excel row positions. Trailing empty formatting rows are not treated as data rows. The original XLSX remains the highest-fidelity source artifact.

The known workbook is expected to produce 5,103 raw rows with source row numbers 3 through 5,105. The parser does not hardcode that count; it preserves the rows actually present. Phase 2A never creates/updates products or barcodes, prices, HPP, inventory, overrides, or audit findings.

### Phase 2B — committed and independently verified

`src/lib/ipos/normalize.ts` and `preflight-engine.ts` implement deterministic normalization and audit-candidate calculation from the immutable `raw_data` snapshot. `runIposPreflight()` in `src/lib/ipos/preflight.ts` verifies the completed batch and raw-row invariants, then reads matching normalized products, active barcodes, and active overrides. It performs SELECT queries only. It does not link import rows or write products, barcode associations, outlet settings, inventory, selling prices, HPP, history, overrides, or audit findings. The report contains per-row proposed actions and a summary plus capped exception samples; invalid numeric values remain errors/null proposals, never zero.

The manual internal route is `POST /api/internal/ipos-preflight` with JSON `{ "batchId": "..." }`. It uses a distinct `IPOS_PREFLIGHT_SECRET` bearer (minimum 32 characters) and the server-only Supabase admin client. Configure this secret only in a trusted operator/server secret store; report data includes proposed HPP and must be treated as sensitive. The route is not linked to the browser. The first controlled production preflight for `eb72f6ad-1cf2-42fb-b899-c894db102c30` has been verified: 5,103 valid candidates, 5,103 new products, no invalid rows, 574 blank barcodes, 2 malformed barcodes, 8 zero/missing HPP, 3 below-HPP, 1,192 zero stock, 873 reorder findings, 3,248 missing rack, 14 duplicate-name groups/29 rows, no numeric errors or override conflicts. The full audit counts matched the independent workbook audit.


The preflight is a point-in-time report assembled from paginated reads, not a database transactionally consistent snapshot. Duplicate name matching is exact normalized-name matching only and never changes identity. Findings are candidates using deployed finding codes; invalid SKU/name and numeric parse errors are preflight diagnostics because an invalid row has no normalized product target (and invalid HPP is not treated as zero). Blank supplier produces no finding.

The trusted route `POST /api/internal/ipos-commit` reran preflight and committed the snapshot transactionally. Production verification confirmed 5,103 normalized products, 5,103 linked raw rows, 4,527 active normalized barcodes, 5,103 inventory rows, 5,103 selling price rows, 5,103 HPP/cost rows, and 5,103 outlet setting rows. The normalization commit is version `ipos-v1-preflight`, status `COMPLETED`. Initial persisted audit findings are: 574 missing barcode, 2 malformed barcode, 8 zero/missing HPP, 3 selling price below HPP, 1,192 zero stock, 873 stock at/below minimum, 3,248 missing rack, and 29 duplicate product-name findings. The initial migration's uniqueness and immutable-source behavior remain as documented.

The Phase 2B migration `20260928143000_ipos_normalization_commit_v1.sql` was applied before the controlled commit, and the production commit was independently verified: 5,103 normalized products linked to 5,103 raw rows, 4,527 active barcodes, and 5,103 rows in each outlet data set. Phase 3A's read-only query migration `20260929100000_product_workspace_read_v1.sql` is applied and powers paged product, audit overview, and read-only detail routes.

### Phase 3A — read-only Product & Audit workspace

`/produk` displays real normalized products with server/database-side search, category/rack exact filters, finding filters (including `NONE` for no open findings), and 25-row pagination. `/audit-produk` shows persisted counts for the latest imported snapshot and links each issue to its filtered product list. `/produk/[id]` is read-only. OWNER and ADMIN see HPP. GUDANG can read permitted operational product data; the database function is `SECURITY INVOKER`, and base-table RLS denies GUDANG cost rows while the returned HPP field is explicitly null. KASIR is denied the workspace by server role checks and receives no cost access under base-table RLS. Browser queries use the session-bound anon-key client; no service-role key is used.

Until native Quena Mart POS is production-ready, iPos remains the transaction system of record. A future phase will import daily iPos sales reports into Quena Mart for analytics/reporting. iPos-imported sales and native Quena POS sales must share a reporting model while retaining source identity (`IPOS_IMPORT` / `QUENA_POS`). The daily sales importer is not part of Phase 3A.

The new migration must be reviewed and applied before the worker can run. A process termination after claim can leave the request PROCESSING with partial raw rows; no automatic reclaim is provided because immutable rows cannot safely be overwritten. Inspect such attempts and preserve them as history; retry by uploading a new snapshot after the incomplete attempt is resolved operationally. The first production request remains manual-only until a controlled test is approved.

### Native product creation

OWNER and ADMIN may create a `QUENA_NATIVE` product from `/produk/tambah`. Native products use the existing `products`, `product_barcodes`, `product_outlet_settings`, `product_inventory`, and outlet-scoped `product_selling_prices` tables. The current selling-price history trigger remains authoritative. Immutable creation and stock-baseline records bind the authenticated actor, active outlet, product, request ID, timestamp, and payload. iPos-imported products retain their `created_from_import_row_id` / import-row provenance; native products have `QUENA_NATIVE` provenance and do not need or receive synthetic iPos provenance.

Native creation does not accept opening stock or HPP. Every native product receives an audited zero-stock baseline (`baseline_quantity = 0`, movement delta = 0, effective stock = 0) in the current stock authority period. It does not create an inventory acquisition or establish WAC/HPP. Final iPos cutover rebases only iPos-derived products from the accepted snapshot; it preserves native zero baselines and advances their period evidence without requiring or fabricating iPos rows. After cutover and costing bootstrap, stock for native products enters through Barang Masuk or another approved stock movement and the existing acquisition costing/WAC path.

The workbook is sheet `Satu Harga`: row 1 is an iPos control row and is not product data; row 2 contains headers; rows 3 onward are product rows. The known workbook contains 5,103 product rows. Preserve the original XLSX in the private `quena-ipos-imports` bucket and preserve every parsed source row as immutable JSONB keyed by exact source header and original Excel row number. Excel formatting/formulas are out of scope. The bucket accepts XLSX MIME only and limits files to 25 MiB.

Every upload creates a new batch/snapshot, even if the file was previously imported. Compute/store a SHA-256 for traceability, but do not reject or overwrite a repeated file. Products missing from a later batch are not deleted. Match/update only on trimmed, case-sensitive exact `KODEITEM`; never use product name as identity. A row can create/update normalized data only when KODEITEM is valid and trimmed and NAMAITEM is nonblank after trimming. If multiple rows in one snapshot contain the same normalized KODEITEM, mark all conflicting rows invalid and leave all raw rows preserved; do not let row order decide the product value. Product SKU is immutable after creation; a changed source SKU is treated as a different product and needs a future audited re-key workflow if it is actually the same item. Other invalid rows remain in `ipos_import_rows` with validation errors and no normalized product link.

Ambiguous/invalid textual numbers are never guessed: preserve raw value, leave the normalized field unchanged/null, and record a field validation error.

### Parsing and validation

- Keep original cell values in raw JSON for all fields, including blanks and invalid values. Also store batch ID and source row number.
- Read Excel numeric cells as numeric values; do not round through JavaScript floating point if the XLSX library exposes a precise decimal representation. Store money to two decimal places and quantities to three; excess precision should be a validation error rather than silent rounding.
- For text numbers, apply Indonesian separators only when unambiguous. For example, `1.234,50` is 1234.50; ambiguous strings are errors. Do not apply currency symbols or guess whether a separator is decimal/thousands when the form is unclear.
- Keep blank barcode as NULL; it is not a row rejection. Any barcode control character makes it invalid for normalized barcode storage; preserve raw and create `MALFORMED_BARCODE`.
- A blank or changed iPos barcode deactivates the previous imported association for that SKU, but does not remove manually-added barcode associations. Each raw snapshot still preserves the earlier value.
- Blank brand is NULL and is not an audit finding in v1. Blank SUPPLIER1 is raw-only and is not a finding.
- Preserve all raw-only source values without interpreting them or inventing enums. Because v1 defines no value vocabularies for these fields, do not flag a value as unexpected until a later specification defines accepted values. Record genuine row parsing/validation errors against the row and workbook/layout errors against the batch.
- For an optional normalized field with a parse error, do not replace a previously valid current value with NULL. Record the error and keep the source snapshot; update only fields parsed successfully.
- On a valid re-import row, a successfully parsed source value is authoritative for its normalized field. A blank optional text field clears that current imported value; an invalid numeric parse does not clear or replace the prior value. Active manual overrides take precedence over the source for all fields.
- OWNER, ADMIN, and GUDANG can upload an XLSX. GUDANG uploads only to `incoming/<auth.uid()>/<uuid>.xlsx` and invokes `request_ipos_import`, which returns only an opaque request ID. GUDANG cannot list/download workbooks or read batches/raw rows. OWNER/ADMIN can list/download files and inspect all batch/raw data. Phase 2A uses the trusted worker only for batch metadata and immutable raw rows; it does not touch HPP, product data, or findings. Privileged credentials remain server-side; authenticated roles have no direct DML grants on these tables.

Numeric destination columns are unconstrained PostgreSQL `numeric` plus explicit checks for nonnegative values and scale (two decimal places for prices/HPP; three for stock). This avoids PostgreSQL typmod rounding before validation. Reject excess fractional scale before writes and preserve the source cell in raw JSON.

The database automatically writes append-only price, HPP, and inventory history whenever normalized current values are inserted or changed. History inherits source row and actor provenance in the same transaction. The import path must submit exact decimal values and actor IDs for service-side writes.

Active field overrides are enforced against normalized updates. Create an override only in the same trusted transaction that applies its corrected value to the normalized field. Import disagreements are system reconciliation events, not human review events; present `PERLU_KOREKSI_IPOS` from unresolved reconciliation state. Phase 3B.1A migration `20260929130000_field_audit_foundation_v1.sql` is applied in production and structurally/security verified; runtime mutation testing remains deferred to isolated staging, and no correction UI is implemented yet. Barcode correction intent is explicit: `ADD_ALIAS` adds another active association without replacing/protecting the iPos source barcode, while `REPLACE_SOURCE` corrects the source association and protects the replacement until re-import agrees or a human decides otherwise. Aliases retain their manual provenance through matching import upserts. Correction request IDs are bound to the authenticated actor and normalized semantic payload; exact retries replay the stored result and a different payload under the same key is rejected. Manual corrections do not rewrite or resolve historical findings. The 49-test static/contract suite passed. Production RPC mutation tests were intentionally not run because separate PostgREST calls cannot be rolled back together and successful calls persist audit/history/request records without guaranteed exact cleanup; full runtime verification must use isolated staging with real authenticated role sessions and synthetic fixtures.

Until native Quena Mart POS is production-ready, iPos remains the transaction system of record. A future phase may import daily iPos sales for analytics; imported and native sales must share a reporting model while retaining source identity (`IPOS_IMPORT` / `QUENA_POS`). Daily sales import is out of scope for Phase 3B.1A.

### Multi-outlet and history

V1 seeds one Quena Mart outlet but keys stock, minimum stock, rack, selling price, HPP, and related history by outlet. Product identity is global. Selling-price, cost, and inventory snapshots retain import-row provenance. A later outlet can use the same product catalog with its own outlet-scoped values.
