# Database

## Existing Supabase schema

The Supabase project already has RLS enabled and contains:

- `public.user_role`: `OWNER`, `ADMIN`, `KASIR`, `GUDANG`.
- `public.profiles`: `id uuid` referencing `auth.users(id)`, `full_name`, `role`, `is_active`, `created_at`, and `updated_at`.
- An OWNER auth user and corresponding OWNER profile.

The application selects only `id`, `full_name`, `role`, and `is_active` for the current profile. Verified remote state: `public.profiles` has only the authenticated self-read policy (`auth.uid() = id`); `anon` has no table privileges; `authenticated` has SELECT only and cannot write, truncate, reference, or trigger the table. The Product & iPos migration did not modify those permissions or policies. The historical profiles migration is archived at `supabase/archive/migrations/20260928_profiles_rls.sql` and must not be run; it is not an active migration.

## Product & iPos Import Schema v1

The deployed schema is `supabase/migrations/20260928_product_ipos_schema_v1.sql`, migration version `20260928`. This file is the database-design source of truth for v1. It did not change `profiles` or its security configuration. Local and remote migration history both record version `20260928`.

The schema seeds one `outlets` row (`QUENA-MART-1`, “Quena Mart”) and scopes import batches, stock, racks, prices, cost, and their history to an outlet. Products have a global, case-sensitive, trimmed `sku` identity. The SKU is immutable after product creation; a changed iPos code is a new identity until a separate audited re-key workflow is designed. Product name is required for normalized product creation but is never an identity. Every uploaded workbook gets a new `ipos_import_batches` snapshot, including row counts and batch validation errors, plus a private Storage object; each source row is preserved in immutable `ipos_import_rows.raw_data` JSONB. Row 1 is excluded from product parsing, row 2 is headers, and source rows begin at row 3.

Normalized tables are `products`, `product_barcodes`, `product_outlet_settings`, `product_inventory`, `product_selling_prices`, and `product_costs`. Selling-price, inventory, and HPP history are separate append-only tables. Barcode associations are nullable at import and may repeat across products; duplicate values are audit findings, not uniqueness violations. Active duplicate barcodes are allowed across products, while a product cannot have duplicate active copies of the same barcode. Imported barcode associations can be deactivated when a later snapshot is blank/changed; manually-added associations are retained. `SUPPLIER1` and the agreed iPos fields with unknown semantics remain in raw JSON only in v1.

Audit data uses `product_audit_findings` for independent snapshot-aware findings and `product_field_audit_reviews` for append-only human field review events. Finding codes and the four field review statuses are enums. A field override is stored separately in `product_field_overrides`; old override rows remain after deactivation. Import disagreements are system reconciliation events, separate from human review. The deployed Phase 3B.1A foundation derives `PERLU_KOREKSI_IPOS` from unresolved reconciliation state.

### RLS and sensitive data

The migration defines an active-profile role helper without changing `public.profiles` grants or policies. Authenticated roles receive read access only; they receive no direct DML privileges on schema tables. Protected product/import writes after Phase 1 must run through trusted server-side handlers using a server-only service credential; that credential must never reach browser code. Phase 1's file upload and request creation use the authenticated browser session and database RPC/RLS. OWNER and ADMIN can read all v1 data, including raw import rows, workbooks, HPP, cost history, and audit data. KASIR can read product, barcode, stock, and selling-price data. GUDANG can read non-cost product, stock, rack, selling-price, and non-HPP audit data, but cannot query batches/raw rows, workbooks, HPP/cost history, HPP overrides, or HPP-related findings/reviews.

GUDANG can upload an XLSX into its own `incoming/<authenticated-user-uuid>/<uuid>.xlsx` path and invoke `request_ipos_import`; the function returns only a request ID. GUDANG cannot list or download any workbook. A future trusted server worker will validate the request, read/parse the private object, and perform batch/raw/cost writes transactionally; no privileged credential is exposed to the browser. The original XLSX remains private and immutable to authenticated clients. OWNER/ADMIN can list and download it; no authenticated role can update or delete snapshots. The bucket has a 25 MiB file limit and allows only the XLSX MIME type. Restrictive anon and authenticated Storage policies close this bucket even if another permissive Storage policy is later added.

Application Phase 1 is implemented at `/import-ipos`: OWNER, ADMIN, and GUDANG can upload the original XLSX with the normal authenticated browser session and create a request for the seeded `QUENA-MART-1` outlet. The UI reads back the caller-visible request state and creation time. If request creation fails after upload, it reports that the private object remains stored and permits retrying the RPC against that same path; it does not attempt a delete. The three-argument RPC also records original filename; the two-argument compatibility overload records the object basename. No service-role key is used by the browser flow.

Phase 2A's follow-up migration is `supabase/migrations/20260928115000_ipos_worker_v1.sql`. It adds the optional request filename for legacy compatibility and SECURITY DEFINER RPCs for atomic QUEUED claim plus batch creation and atomic completion/failure. These functions are executable only by `service_role` except the authenticated request-creation overload. The worker inserts only `RAW_ONLY` rows with null product links; it cannot complete a snapshot unless stored row count and contiguous source numbers match. A process crash may leave a PROCESSING attempt for manual investigation; automatic reclaim is intentionally absent because the snapshot rows are immutable. The verified real Phase 2A snapshot contains 5,103 raw rows, Excel rows 3–5,105, and no product links.

The Node-only worker downloads only from `quena-ipos-imports` using a server-only service key. The manual internal route requires a separate bearer secret (`IPOS_IMPORT_WORKER_SECRET`, minimum 32 characters). Both must be server environment variables, never `NEXT_PUBLIC_*`. Phase 2A writes only `file_sha256`, batch lifecycle/count/error metadata, request lifecycle, and raw rows. It does not write product, barcode, inventory, selling-price, cost/HPP, override, review, or audit tables.

Phase 2B preflight (`POST /api/internal/ipos-preflight`) is a read-only server operation protected by `IPOS_PREFLIGHT_SECRET` and the server-only admin client. It verifies the completed batch's row count, Excel row sequence, outlet, RAW_ONLY status, and null product links before loading raw rows and SELECT-only normalized reference data. It returns normalization proposals, prospective exact-SKU create/update actions, audit candidates, and override conflicts. It performs no database writes and does not invoke RPCs. The report can contain proposed HPP, so its bearer secret and response are restricted to trusted operators. It was verified against production batch `eb72f6ad-1cf2-42fb-b899-c894db102c30`, matching the independent workbook audit exactly.

The commit implementation is `POST /api/internal/ipos-commit` plus `public.commit_ipos_normalization(uuid,text,jsonb)` in applied migration `20260928143000_ipos_normalization_commit_v1.sql`. It uses a distinct `IPOS_COMMIT_SECRET`. The route rebuilds the proposal using the same preflight normalizer; it does not accept caller-supplied product data. The RPC locks the batch and advisory lock `(734921, 2)`, compares current product/barcode/override state with the fresh preflight state, then performs the writes in one RPC transaction. A unique `(batch_id, normalization_version)` commit record provides idempotency. The initial 5,103-product production commit completed and was independently verified.

Phase 2A batch status remains `COMPLETED`; separate `ipos_normalization_commits` tracks the normalization lifecycle. Its child rows preserve per-row proposals, override-conflict fields, and result provenance; OWNER/ADMIN can read these rows, while GUDANG/KASIR cannot. A guarded trigger allows each raw row to transition once from `RAW_ONLY` to `VALID` with a product link or `INVALID` without one, only while a matching commit is active. `raw_data` remains immutable. The migration removes service-role direct write privileges on normalized target tables and raw-row UPDATE; the trusted RPC is the only commit path. The Phase 2A worker retains raw-row INSERT and batch/request lifecycle privileges. Override conflicts are recorded on the private commit proposal; a human review event is not fabricated. Future normalized writer functions must acquire advisory lock `(734921, 2)`.

Raw-row JSON and source identity are immutable, batch lifecycle transitions are guarded, and authenticated roles cannot write raw tables directly. Selling-price, HPP, and inventory changes create database-managed append-only history rows in the same transaction. Active manual overrides must match their normalized current value when created; updates that change an overridden field away from the corrected value are rejected. The trusted importer must catch that conflict, leave the override in place, and record the iPos disagreement for review instead of overwriting it.

### Constraints and indexes

The migration includes composite foreign keys that tie normalized values and findings to a source row, product, batch, and outlet where applicable. SKU uses a unique, case-sensitive `C` collation constraint and rejects blank values, surrounding whitespace, and control characters. A valid SKU and nonblank name are required for normalized product creation; invalid rows stay in the raw snapshot. Numeric columns use unconstrained `numeric` with explicit nonnegative, equivalent `numeric(14,scale)` range, and exact scale checks (two decimals for money, three for quantity), so PostgreSQL cannot silently round excess scale or accept non-finite values. Indexes cover batch chronology/status, source-row lookup, barcode lookup, normalized product-name matching, outlet-scoped stock/pricing, history chronology, and open audit findings. No global barcode uniqueness is enforced.

See [iPos Import](IPOS_IMPORT.md) for the exact 24-column mapping and parsing contract, and [Product Audit Rules](AUDIT_RULES.md) for finding and correction lifecycle.
# Product workspace read path — Phase 3A

The normalized schema remains the source for product master, active barcode, outlet price/cost/inventory/rack settings, and persisted audit findings. Product browse reads are paginated and filtered in Postgres through the proposed `product_workspace_list`, `product_workspace_detail`, and `product_audit_overview` functions in `20260929100000_product_workspace_read_v1.sql`. These read functions use `SECURITY INVOKER` so existing table grants and RLS apply. The small `product_workspace_latest_snapshot` `SECURITY DEFINER` helper returns only the latest completed batch/outlet identifiers to authenticated active profiles because normalization commit metadata is manager-only; the helper does not return raw rows, product values, or HPP.

Cost rows remain protected by the existing `costs_select_managers` policy (OWNER/ADMIN only). The product functions explicitly project HPP only for OWNER/ADMIN, and RLS prevents GUDANG/KASIR from joining cost rows. The app additionally displays HPP only to OWNER/ADMIN; UI hiding is supplementary, not the security boundary. No service-role client participates in browser product reads. Phase 3A migration `20260929100000_product_workspace_read_v1.sql` and Phase 3B.1A migration `20260929130000_field_audit_foundation_v1.sql` are applied. Production post-migration structural/security verification passed; runtime mutation verification remains deferred to isolated staging.

Phase 3B.1A separates source findings, append-only human review, and system reconciliation events. Corrections are limited to barcode, rack, HPP, and selling price; quantity and minimum stock remain informational. Barcode RPCs require an explicit `ADD_ALIAS` or `REPLACE_SOURCE` operation. `ADD_ALIAS` retains current barcode associations, creates a manual association without a source-replacement override, and preserves its NULL source pointer through import upserts. `REPLACE_SOURCE` retires active imported/source associations while retaining their rows as inactive history, preserves NULL-provenance manual aliases, and protects the replacement with an active source-bound override until import agreement or an explicit decision. OWNER/ADMIN alone can access HPP correction/source/reconciliation values. GUDANG can review and correct barcode/rack through narrow source projections. KASIR has no field-audit access. No direct authenticated DML is added. A private correction-request table binds each request UUID to the authenticated actor and normalized semantic payload (product/outlet, field, source row, operation, corrected value, and reason). Under the shared advisory lock, an identical retry returns its original result; reusing the UUID with a different payload raises `IDEMPOTENCY_KEY_REUSED`. Production structural/security verification passed. Runtime mutation testing remains pending in isolated staging; the phase is not described as end-to-end runtime verified.
